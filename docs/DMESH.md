# Dmesh — the node network

*[فارسی](DMESH.fa.md)*

Dsp32 runs on one board. Dmesh is how it drives others.

A **Di8266 node** is an ESP8266 running the client firmware in
[`esp8266/`](../esp8266). It is not a second desktop and does not try to be:
it raises its own access point, answers discovery, and hands its pins over to
the Dsp32 board. The **Dmesh** app on Dsp32 finds nodes, names them, takes
ownership of them, drives their pins and pushes new firmware to them over the
air.

A node keeps its own name, key, access point, pin modes and rules in EEPROM,
so it carries on doing its job with the board switched off. The board keeps
the same picture, so a node that has been unplugged is put back the way it was
when it returns. Neither side depends on the other being awake.

---

## The short version

| | |
|---|---|
| **Default network** | `Di8266`, password `123@Test`, on `192.168.8.1` |
| **Protocol** | Dmesh v2 over UDP, port `32700` |
| **Per-frame security** | AES-128-CTR + HMAC-SHA256, one key per node |
| **Node count** | No fixed limit; the registry grows on demand |
| **Pins exposed** | `D1`–`D8` digital/PWM, `A0` analogue |
| **Rules per node** | 8, run on the node itself |
| **Node firmware** | ~315 KB flash, ~30 KB RAM |
| **First flash** | USB, once per board |
| **Later updates** | Over the air from Dsp32 |

## What manages what

The board is the controller and the app is a view onto it. The registry, the
keys, the desired state and the reconciliation all live in the firmware — so
closing the Dmesh window, reloading the page or walking away for a week
changes nothing about whether the network is being managed.

That has one consequence worth stating plainly, because the whole design
follows from it:

> **You configure a node, not a connection.** What a node should be is written
> down the moment you ask, whether or not it is plugged in. When it next
> reports in, the board notices its state is not the one that was asked for
> and fixes it.

So a node that is switched off is not an error and not a queue of pending
commands. It is a node that is not currently in sync, and the app says so.
Plug it in and it is corrected within one heartbeat.

## Why the controller does not poll

Version 1 had the board ask each node how it was. That is O(n) work on the one
part that must not get busy, and it scales exactly the wrong way: fifty nodes
meant fifty round trips with fifty timeouts to wait out.

Nodes push instead. A node announces itself when it boots and sends a
heartbeat every eight seconds; the board sits on one socket and does nothing
until a frame arrives. Every heartbeat carries a 32-bit hash of the node's own
state, so deciding whether a node needs anything is **one integer comparison**.
A node that is already correct costs that and nothing else.

This is why the node count does not matter. There is no per-node timer, no
per-node socket, no scan that walks the list. Adding the hundredth node costs
one more heartbeat every eight seconds.

## Why a protocol of its own

A node is an 80 MHz part with about 40 KB of usable heap. HTTP would cost it a
TCP accept, a header parse and a socket per exchange; mDNS discovery would
cost it a multicast listener it has to keep up all the time. Neither is
affordable on a part that also has to answer a pin change in under a
millisecond.

Dmesh is one UDP datagram per message. The node keeps no connection state at
all, discovery is a broadcast it answers in a few hundred microseconds, and
the whole implementation is under 300 lines.

What that costs is that UDP can drop and reorder packets, and the design
answers that rather than ignoring it:

- every frame carries a counter the receiver checks, so a duplicate or a
  reordered frame is dropped rather than acted on twice;
- nothing depends on a single frame arriving. A lost command is noticed at the
  next heartbeat, because the node reports a state that is not the wanted one
  and gets corrected. The mechanism that handles a node being switched off
  handles a dropped packet too, with no retry logic of its own;
- nothing streams, so there is nothing for a lost packet to corrupt.

The wire format lives in one header,
[`esp8266/include/dmesh_proto.h`](../esp8266/include/dmesh_proto.h), which both
firmwares compile against. There is no second copy to drift.

### Security

Every node has its own **16-byte master key**, generated by the board's
hardware random generator at claim time. No two nodes share one, and the keys
never leave the board — the REST API takes a node id, never a key, so a key
cannot leak through a page or a screenshot.

Both sides derive two subkeys from the master with SHA-256, so the key that
encrypts is never the key that authenticates:

```
enc = SHA256(master || "dmesh-enc-v2")[0..15]
mac = SHA256(master || "dmesh-mac-v2")[0..15]
ct  = AES-128-CTR(enc, nonce = bootId || counter, plaintext)
tag = HMAC-SHA256(mac, header || ct)[0..7]
```

Encrypt-then-MAC, so a forged frame is thrown away before anything decrypts
it. The counter is both the CTR nonce and the replay guard: a receiver
remembers the highest it has seen and drops anything at or below it, so a
captured frame cannot be replayed. A node picks a random **boot id** at
startup, which is what tells a genuine restart — where the counter legitimately
returns to zero — from an attack.

Eight bytes of tag is short for a file format and correct here: forging one is
2^64 tries against a node that answers a few hundred frames a second, and
every extra byte is a byte in every datagram on a network where the datagrams
are the cost.

**The one weak moment is claiming.** The key is handed over in the clear,
once, so anyone listening at that exact instant gets it. Two things narrow it:
a node only accepts a claim during its **first two minutes after power-on**,
and a node that already has a key will not take another. Claim on a network
you control, and power-cycle a node if you need to claim it later.

Discovery is answered whatever the key, deliberately — a node whose key you
have lost still has to be findable, or the only way back is a serial cable. It
carries nothing but the name, the id and whether the node is already claimed.

## Getting the firmware onto a blank board

There are two ways, and the first one needs no cable at all.

### From Dsp32, over four wires

A blank ESP8266 cannot be discovered — it has no firmware to announce itself
with — and cannot be updated over the air for the same reason. But every one
of them has its bootloader in mask ROM, which cannot be erased and is there on
a chip that has never been programmed. Dsp32 speaks it.

Press **+** in Dmesh, wire four pins, pick them in the dialog:

```
Dsp32 TX   →  ESP8266 RX
Dsp32 RX   ←  ESP8266 TX
Dsp32 pin  →  ESP8266 GPIO0
Dsp32 pin  →  ESP8266 RST
GND        ─  GND
```

GPIO0 and RST are what make this possible at all. Holding GPIO0 low through a
reset is how the part is put into its bootloader, and without those two wires
that can only be done by hand — which a firmware cannot do. The rest is the
ROM loader's own protocol: SLIP framing, a sync, an erase, then the image a
kilobyte at a time. About a minute at 115200 baud.

Deliberately no stub loader is uploaded first. A stub is faster and can
compress, but it is a second binary to carry, keep current and get wrong; the
ROM loader is already on the chip and once is fine.

The image comes from `esp8266/firmware/di8266.bin` in this repository, fetched
through the board and cached — on the SD card if there is one, so the next
board does not download it again.

### From a computer, over USB

You need [PlatformIO](https://platformio.org/). The Arduino IDE will not do —
the partition layout matters and PlatformIO sets it.

```bash
./esp8266/build.sh                # builds and publishes firmware/di8266.bin
cd esp8266 && pio run -e di8266 -t upload
```

`build.sh` copies the image to `esp8266/firmware/` and writes a manifest with
its version and digest beside it. That is what Dmesh fetches, so the published
image cannot drift from the source it was built from.

The flash is split 512 KB for the sketch and the rest for OTA. That split is
what makes an over-the-air update possible at all: the new image is written to
the spare half and only becomes the boot image once it is complete and its
checksum passes. **A node that loses power mid-update comes back running the
old firmware.**

A USB cable is needed exactly once per board. Everything after that is over
the air.

### What a fresh node does

```
Di8266 2.0 — "Di8266-9B4401"
  AP:   Di8266
  IP:   192.168.8.1
  Mesh: UDP 32700, unclaimed — waiting for Dsp32
```

It raises `Di8266` / `123@Test`, names itself from the last three bytes of its
MAC so two on a bench are told apart, and waits. All pins are inputs, which is
the safe state for whatever is wired to them.

## Connecting it to Dsp32

**Nothing.** A node joins the Dsp32 hotspot on its own and announces the
moment it associates, so it appears in the app within a second or two of being
powered up. **Scan** exists to hurry that along, not because anything needs it.

This is what makes the node count irrelevant. Every node is a station on the
board's own hotspot, so they all share one subnet: the controller broadcasts
once and hears from all of them, and the twentieth node changes nothing about
the arrangement. A node that instead sat on its own network could never be
reached by the controller, and there could only ever be one of them — a Dsp32
board joins exactly one network.

The node still raises its own `Di8266` access point alongside. That is the way
back in, not the way it is used: it is always up, it does not depend on the
board being switched on, and it is what the OTA bridge talks to.

**The one case that needs a hand.** A node ships knowing the *default* hotspot
name and password, because that is all it can know before anyone has spoken to
it. If you changed either before a node was ever claimed, it has nothing to
join. Join its `Di8266` network from **Settings → Network** (password
`123@Test`), claim it once, and the board hands it the real credentials — after
which it finds its own way home, and you can leave `Di8266` behind.

Claiming always sends the current hotspot credentials, so changing your
password later and re-claiming is enough to move a node across.

## Using the app

Install **Dmesh** from the App Store. It is not in the firmware — no
installable app is.

**Scan** broadcasts and lists what answers. Each node shows a dot:

| Dot | Meaning |
|---|---|
| Grey | Unclaimed — anybody can take it |
| Green | Claimed, and this board holds the key |
| Amber | Claimed by someone else |

**Claim** generates a random 32-bit key, sends it to the node, and stores it.
From then on only this board can drive that node. Claiming a node someone else
owns takes it over, and the app says so before it does it.

**Pins** are laid out as they are silkscreened — `D1`–`D8`, `A0` — not as raw
GPIOs, because nobody reading a NodeMCU sees "GPIO 4". Each pin gets a mode:

| Mode | Pins | Notes |
|---|---|---|
| input / input + pull-up | D1–D8 | |
| output | D1–D8 | toggled with the HIGH/LOW button |
| PWM | D1–D8 | 0–1023, dragged on a slider |
| analogue | A0 only | 0–1023 counts |

Modes are saved to the node's EEPROM. Output *levels* are not: a pin toggling
in a loop would wear the EEPROM out in an afternoon.

The pins a node cannot do are refused by the node, not hidden by the app —
asking A0 for PWM gets "that pin cannot do that" back from the hardware
itself.

### Rules

A rule is a job handed to the node. It runs **on the node**, which is the whole
point: a threshold that has to ask the board before it can act has the
network's reaction time, and a board that has to be asked is doing *n* jobs
instead of one. Rules survive the node rebooting and keep working with the
board switched off.

Up to eight per node, in four shapes:

| Kind | Does |
|---|---|
| **Threshold** | While the watched pin is over/under a value, drive another pin. Releases when the condition stops, or holds for a set time to make it a pulse. |
| **Edge** | Fires once on the transition into the condition, not for as long as it stays there. |
| **Report** | Sends a reading to the board when it moves by more than a given margin. Without that margin an analogue pin reports forever. |
| **Blink** | Toggles a pin on a timer — a heartbeat LED that proves the node is alive without anything asking it. |

A rule stays until you disable or delete it. It is a task, not a command.

### Releasing a node

Two different things, and the difference matters:

**Release and wipe** tells the node to erase itself — its key, its pin
settings and its rules all go — and it comes back as a blank node anyone can
claim. This is what to do before handing the hardware to someone else. The
node is told first and forgotten second; the other order would leave it
holding a key nobody has, which is the one state there is no way out of
without a serial cable.

**Forget on this board only** stops managing it here while the node carries on
doing whatever it was doing. Use this when the hardware is gone and cannot be
told anything.

**Access point** changes the node's SSID, password and whether it is hidden.
The radio restarts, so the node vanishes for a moment and has to be found
again. Hiding an SSID is not a security measure — anything watching the air
sees the node as soon as something connects — it just keeps it off everyone's
phone.

## The OTA bridge

Updating a node from Dsp32 has one wrinkle: the node is on the board's little
network, not the internet. It cannot reach GitHub.

So the bridge works in three steps, and the app does all of them:

1. **Dsp32 downloads the image** through its own outbound proxy, which needs a
   Wi-Fi uplink, and writes it to the filesystem.
2. **Dsp32 serves it back** over its own HTTP server and tells the node the
   URL. The node fetches from the board's AP address, which is the one address
   it is certain to be able to reach.
3. **The node flashes it**, verifies it, and reboots into it.

Before the flash starts the node drives every output low. An update takes tens
of seconds and ends in a reboot; a relay left energised through all of that is
how equipment gets damaged.

### Where the image goes afterwards

**With an SD card**, the image is kept at `/sd/Firmware/di8266.bin` so the next
node does not have to download it again.

**Without one**, it is deleted from the internal flash 45 seconds after the
node starts pulling it. A 309 KB file is a serious fraction of the internal
flash, and holding it there to save one download is a bad trade on a board
this size. This is the same rule the rest of Dsp32 follows: the firmware ships
nothing it can fetch, and keeps nothing it does not need.

## The REST API

The desktop is a browser. A browser has no UDP and no broadcast, so the board
holds the socket and the desktop drives it — the same arrangement as the
outbound HTTP proxy, for the same reason.

Every route takes `id`, the node's MAC, because that is the only stable name a
node has; its address is a lease. All of them except `discover` take `key`.

| Route | Method | Does |
|---|---|---|
| `/api/mesh/list` | GET | Every registered node, online or not |
| `/api/mesh/discover` | GET | Broadcast, then the list |
| `/api/mesh/claim?id=` | POST | Give it a key of its own |
| `/api/mesh/revoke?id=&wipe=1` | POST | Wipe it, or just forget it with `wipe=0` |
| `/api/mesh/desired?id=` | POST | Its desired state, as a JSON body |
| `/api/mesh/write?id=&pin=&value=` | POST | Drive an output now |
| `/api/mesh/pwm?id=&pin=&value=` | POST | Set a duty cycle, 0–1023 |
| `/api/mesh/read?id=` | GET | Ask for a fresh report |
| `/api/mesh/reboot?id=` | POST | Restart the node |
| `/api/mesh/ap?id=&ssid=&pass=&hidden=` | POST | Change its access point |
| `/api/mesh/ota?id=&url=&size=` | POST | Point it at a firmware image |

`desired` takes the whole state in one body, because it has to be applied as
one thing — a half-written state pushed to a node is worse than none:

```json
{
  "name": "greenhouse",
  "modes":  [3, 1, 0, 0, 0, 0, 0, 0, 5],
  "values": [1, 0, 0, 0, 0, 0, 0, 0, 0],
  "rules": [
    { "kind": 1, "src": 8, "dst": 0, "cmp": 0,
      "value": 600, "action": 1, "holdMs": 0, "enabled": true }
  ]
}
```

`modes` is one entry per pin in `D1`…`D8`, `A0` order, using the mode numbers
in the table above. It works on an offline node: the state is recorded and
applied when the node returns.

## In a flow

Diba Manager gains a **Mesh** group with **Node in** and **Node out**, so a
flow can read a sensor on one node and drive a pin on another. The pickers
list every claimed node, offline ones included — a flow referring to a node
that is currently unplugged is not wrong.

Node in reads from the board's cache of what nodes last reported rather than
asking the node, so a flow ticking four times a second costs the network
nothing. Node out only sends when the value actually changes.

A pin's *mode* is set in Dmesh, not in the flow: a flow drives a pin, it does
not decide what the pin is.

## Testing without hardware

The simulator carries two stand-in nodes that behave the way the firmware
does — unclaimed until a key is set, pin modes persisting, levels not, and the
same refusals for a pin asked to do something it cannot.

```bash
python3 simulator/dsp32_sim.py --port 8000
```

Then install Dmesh from the App Store and press Scan.

## Limits worth knowing before you build on it

- **Eight rules** per node. That is what a node has EEPROM for.
- **Twelve pins** in the protocol, nine on the hardware.
- **Claiming is trust-on-first-use**, inside a two-minute window. See above.
- The registry has no fixed size, but NVS on the board runs out somewhere
  around two hundred nodes.
- **No mesh routing** despite the name. Every node talks to the board
  directly; nodes do not relay for each other. A node out of the board's radio
  range is out of reach.
